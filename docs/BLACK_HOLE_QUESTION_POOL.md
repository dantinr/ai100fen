## 1. 目标与边界

将现有“问题池”入口的 UFO 动效调整为“黑洞”，并在问题池页面将“与 Z 一起定义问题 → 用户确认 → 提交成功”设计成完整交互。不要把旧 UFO 删除：它仍是 Z 的飞行器，用于探索、课程进度和任务完成等场景。

三种元素必须形成稳定的产品语义：

| 元素 | 语义 | 主要场景 |
|---|---|---|
| 黑洞（Black Hole） | 收集未知、接收经过确认的问题 | “问题池”导航、问题池页面、确认提交成功 |
| Z | 与用户对话，澄清需求，帮助定义问题 | 问题池聊天、任务卡生成、课程引导 |
| UFO | 探索和执行的视觉符号 | 首页探索、课程进度、后续任务流程 |

**严格区分**：“开始聊天”不等于“提交问题”；只有用户明确确认，问题才会被保存或公开发布。不得用动画掩盖失败，也不得在服务端确认成功之前显示成功态。

本任务是现有产品的渐进式改造，不得重新实现另一套问题池、Z 聊天系统或主题系统。

## 3. 信息架构与文案

导航名称暂时保持 **“问题池”**，以免现有用户产生路径认知断裂；视觉语义升级为“问题黑洞”。在问题池页强化黑洞叙事，而不是将所有按钮都写成“黑洞”。

- 页面主标题：**把问题扔进黑洞。**
- 页面副标题：**告诉 Z，你遇到了什么问题。**
- Z 的示例开场：**“说吧，今天想搞定什么？我们先把问题想清楚。”**
- 对话入口 CTA：**“开始与 Z 对话”**
- 生成任务草稿后：**“确认并提交问题”**（根据实际业务，可以拆为“保存私人草稿”与“发布到问题池”两个明确动作）。
- 服务端确认成功：**“问题已收集。”**

保持 AI100分 的三个核心分类：`solve`（解决一个问题）、`create`（创作一个作品）、`explore`（探索一个可能）。Z 可建议分类，但用户始终可以检查/修改任务卡。

## 4. 导航：黑洞取代 UFO Hover

### 4.1 默认态

- 顶部导航仍显示“问题池”；不新增布局高度或挤压其他导航项。
- 黑洞默认隐藏，或者以极小的静态标记呈现；避免持续旋转和消耗资源。
- 点击导航仍正常进入现有问题池路由，动效绝不可覆盖点击区域。

### 4.2 桌面悬停/键盘聚焦态

1. 鼠标 Hover 或键盘 `focus-visible` 时，在“问题池”标签附近显示小型原创黑洞 SVG（示意 32–48 px，按导航实际尺寸调整）。
2. 吸积盘轻微旋转、中心保持稳定，导航文字出现主题化高亮。
3. 鼠标离开 / 焦点离开时，黑洞渐隐、动画停止；建议进入/退出分别在 180–300 ms 内完成。
4. 黑洞、光效层统一 `pointer-events: none`，不产生 Hover 抖动或悬停区域断层。

**禁止**：强闪烁、大范围页面扭曲、全屏遮罩，以及黑洞把导航文字吸走导致用户无法阅读/点击。

### 4.3 手机和平板

- 手机端无 Hover：显示静态微型黑洞图标或直接不显示；用户点击仍直接导航。
- 不允许动画延迟页面跳转。
- 明确支持键盘操作与清晰可见的焦点反馈。

## 5. 问题池页面：与 Z 对话

采用现有布局，不强制推倒重做。若适合双栏，可使用：

- 左侧：Z 对话区（用户输入、Z 提问、推荐项、聊天历史）；
- 右侧：实时生成的“任务草稿”（目标、范围/限制、期望产出、分类、验收标准），可由用户手动编辑；
- 移动端：聊天主区域，任务草稿折叠或置于聊天下方。

### 5.1 用户旅程

```text
进入问题池
  ↓
与 Z 对话：自由描述想法
  ↓
Z 澄清需求并推荐 Solve / Create / Explore 类别
  ↓
实时形成可编辑的任务草稿
  ↓
用户查看并确认提交
  ↓
调用现有问题池后端接口
  ├─ 失败：保留输入与草稿，展示错误及重试
  └─ 成功：触发黑洞吸入动画 → 显示成功信息 / 查看入口
```

**隐私边界：** 聊天内容和任务草稿默认不公开。即使保存了对话，也不得暗中把私人聊天全文发布到公共问题池。若现有业务中“提交”默认公开，必须在确认步骤清楚告知用户将公开哪些字段；若支持私人草稿，分别显示其状态。

### 5.2 Z 的职责

- 帮用户明确：**想解决什么问题 / 做出什么作品 / 验证什么可能**；
- 追问必要的目标、约束、期望结果，但不要将对话变成冗长表单；
- 输出可编辑的任务卡；
- 若存在匹配课程，可在不打断当前对话的情况下推荐课程；
- 无匹配课程时，提供“提交到问题池”路径；
- 不承诺课程一定会制作，不承诺问题一定能解决。

可沿用 Z 的 `idle`、`thinking`、`idea`、`got_it`、`so_so`、`awkward` 状态，**本期不需重做角色 SVG 或引入新模型**。

## 6. 黑洞确认提交动效

### 6.1 动画时序

| 阶段 | 触发 | 表现 | 规则 |
|---|---|---|---|
| A · Ready | 用户确认前 | 黑洞静态/极慢旋转，任务卡可编辑 | 不暗示已提交 |
| B · Sending | 用户点击确认 | 按钮进入加载态；可展示轻微吸积盘旋转 | 禁止重复提交，保留草稿 |
| C · Success | 服务器返回成功 | 任务卡副本沿曲线路径向黑洞移动、缩小、淡出 | **仅成功后**触发吸入 |
| D · Received | 动画结束 | 显示“问题已收集”及查看入口 | 有真实问题 ID 时提供链接 |
| E · Error | 请求失败 | 停止待提交动画；恢复按钮与草稿，显示可恢复错误 | 不能出现成功提示 |

建议完成动画总长 500–900 ms，上限约 1 s。避免因动画造成操作迟滞：在完成动效期间可立即向用户展示语义明确的成功文字。

### 6.2 视觉

- 黑洞核心为深色圆形，外围为旋转的橙黄吸积盘，少量紫色作为强调；符合当前 Pop Art 风格。
- 使用原创 SVG / CSS 实现，不直接使用受版权保护的科幻影视素材。
- 卡片只对**视觉副本**做 `transform` / `opacity` 动画，原始数据及真实任务卡状态由应用管理。
- 黑洞表达“收集”，而不是“删除”；提交后必须能找到已收集问题。

### 6.3 不要做的事

- 不要在用户输入期间吸走文本；
- 不要提交前就宣称“已收集”；
- 不要以黑洞动画替代错误处理；
- 不要采用大型 WebGL、视频背景、过量粒子或全屏转场；
- 不要将任务卡 DOM 真正销毁以代替状态更新。

## 8. 主题兼容

本需求必须使用当前 Theme System，不得将 Pop 视觉硬编码到业务页面。

- `pop`：粗黑线、橙黄吸积盘、平面漫画纹理、克制的硬阴影；
- `future`：暗色空间、细线 HUD、柔和光晕；只需实现可用的主题骨架，不要求本期做完整 Future 动画；
- `minimal`（如果未来增加）：低装饰、静态图形。

将颜色、光晕、线宽、背景、速度等抽象为主题 Token 或主题内配置，页面结构与提交行为不随主题复制。

## 9. 可访问性和性能

1. 支持 `prefers-reduced-motion: reduce`：取消旋转、曲线路径、缩放；成功后直接切换到“问题已收集”静态反馈。
2. 状态不能只依赖颜色或动画表达；成功/失败必须提供明确文字，必要时 `aria-live` 通知。
3. 黑洞视为装饰元素时设置 `aria-hidden="true"`，主导航本身保留可识别名称。
4. 输入框和确认按钮保持键盘可访问，移动端点击区域合理。
5. 动画优先 SVG + CSS `transform` / `opacity`，不强制加载大型 JS 库。
6. 与真实接口联调前，不允许把纯前端演示成功当成真实提交成功。
7. 核对慢网络、请求超时、重复点击、服务端 4xx / 5xx 的表现。
