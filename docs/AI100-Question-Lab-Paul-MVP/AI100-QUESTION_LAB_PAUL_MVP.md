# AI100分 · 问题探索工作台（Paul Chat）MVP

> 状态：Codex 可执行规格 · v1.0
> 页面：现有「问题池」
> 品牌：Solve / Create / Explore + 可替换 Theme System
> 目标：私人多轮探讨 → 结构化任务卡 → 用户确认 → 可选提交公共问题池

## 1. 产品决策

把「问题池」由“填表提交问题”改为“与 Paul 一起探索问题”的聊天工作台。保留公开问题发现/投票能力（如现有功能），不删旧数据。

- Paul 首先帮用户说清问题、目标和边界，而不急于推销课程。
- 每次最多追问 **一个**最重要的缺失信息，支持用户跳过。
- 对话应逐步产出 **任务草稿**；其余聊天消息默认不公开。
- 用户在提交前预览和编辑任务卡，明确选择“加入问题池”；**不能因为发送聊天消息就自动公开**。
- 如果用户只想解决私人问题，可保留私人草稿或直接查看已有课程；不强制发布。
- 分类遵守 COURSE_CONSTITUTION：`solve | create | explore`，每个最终任务卡只有一个主分类。
- Paul 是外星人风格的 **原创角色**，不复刻影视角色形象、声音或台词。

### V1 必须完成的闭环

`进入问题池 → 与 Paul 聊天 → 收集关键条件 → 右侧实时更新任务卡 → 用户编辑确认 → 提交到问题池（待审核） → 返回问题编号/状态`

## 2. 页面信息架构

桌面端：

- 顶部：`QUESTION LAB`、标题“和 Paul 聊聊你的问题”、辅助文案。
- 左侧主区（约 2/3）：Paul 头像 / 对话 / 快捷提问 / 输入框 / 发送、重试。
- 右侧（约 1/3）：实时任务草稿：分类、标题、当前障碍/意图、期望结果、限制条件、完成标准、是否适合 100 分路线；允许编辑。
- 次级入口：`看看大家在解决什么`，进入原有公开问题列表，不让聊天功能吞掉社区发现。
- 可增加已有课程推荐卡，但只能推荐数据库里**真实存在且可访问**的课程。

移动端：聊天优先；任务草稿折叠成底部按钮或独立抽屉；不遮挡输入法和发送按钮。

### V1 页面文案

- H1：`有什么问题？和 Paul 聊聊。`
- 副标题：`不需要先写需求。把想法扔过来，一起把它变成能执行的任务。`
- Paul：`你今天想解决一个问题、做一个作品，还是探索一个可能？`
- 输入框：`比如：我每天要合并几十个 Excel，不想再手工整理……`
- 草稿标题：`正在形成你的任务卡`
- 主提交按钮：`确认，加入问题池`
- 公开前说明：`只有你确认的任务卡会被提交；聊天记录默认不公开。`

## 3. Paul 的对话策略

结合 PAUL_PERSONA_LINES.md 与 PAUL_EXPRESSION_SPECS.md。角色必须帮助用户推进，而不是漫无目的陪聊：

1. `discover`：识别意图，不确定时只追问最必要的一个问题。
2. `clarify`：确定用户当下的障碍/想要的成品/想验证的假设。
3. `scope`：识别预算、时间、现有条件、边界等必要信息。
4. `propose`：提出任务草稿，必要时给出一条最短可验证路径。
5. `confirm`：请用户审核草稿（允许改写），**用户主动点击提交**。
6. `next_step`：显示问题池状态或提供已存在课程的链接。

禁止：虚构课程/价格、声称已提交而没有成功响应、公开私人对话、让不完整问题自动变成付费课程。

### 表情动作协议

| `expression` | 触发条件 | 动画 |
|---|---|---|
| `idea` 灵机一动 | 发现可行方案/新的任务拆解 | 抬头 + 星形闪光（单次） |
| `got_it` | 用户目标明确/操作真实成功 | 点头（单次） |
| `so_so` | 信息不足/只能给有条件的建议 | 轻摊手 |
| `awkward` | 没理解/服务异常/无法可靠回答 | 眼神移开 + 小汗滴 |
| `idle`/`thinking` | 等待/生成回复 | 轻微呼吸/短暂思索 |

注意：状态由聊天控制器的结构化响应驱动，服务端只允许白名单 enum；不要让原始模型输出直接注入 DOM/CSS。

## 4. 任务卡结构（是核心资产）

建议最小字段：

```json
{
  "category": "solve",
  "title": "自动合并每天收到的 Excel 文件",
  "user_intent": "不想再人工整理每日表格",
  "current_blocker": "多份表格格式略有差异",
  "final_outcome": "自动生成一份标准汇总表",
  "constraints": ["不上传客户原始数据"],
  "completion_criteria": ["测试样本处理成功", "输出字段核验通过"],
  "agent_role": "编写本地脚本并解释执行结果",
  "human_judgment_required": "核验数据与隐私边界",
  "visibility": "private"
}
```

- `title`, `category`, `user_intent`, `final_outcome` 在公开提交前必填。
- `completion_criteria` 至少一条，Explore 可以是完成实验并形成有证据的结论，而非“实验一定成功”。
- `constraints` 可以为空，不得擅自编造用户限制。
- `visibility` 默认 `private`；用户提交并通过服务端确认后，状态进入 `pending_review`，不自动变成公开帖子。
- 如发布需要匿名选项，界面上明确显示身份暴露范围。

## 5. 模型与后端

先审计现有 Laravel 项目、路由、用户、问题池模型、课程表、PaulChatWidget。**扩展已有实现，禁止平行新建第二套聊天系统或覆盖历史数据**。

可参考的接口契约（路由可根据现有项目调整）：

```
POST   /api/paul/conversations              开启私人会话
POST   /api/paul/conversations/{id}/messages 发送消息并返回 Paul 回复和任务草稿增量
GET    /api/paul/conversations/{id}          恢复本人会话（如实现登录持久化）
PATCH  /api/paul/conversations/{id}/draft    用户编辑/保存草稿
POST   /api/paul/conversations/{id}/submit   提交经确认的任务卡到问题池
```

推荐响应对象：`reply`, `expression`, `stage`, `draft_patch`, `suggested_actions`, `recommended_course_ids`, `conversation_id`。所有模型输出必须经过服务端 schema 验证；课程 ID 在本地数据库核验存在、发布状态与可访问性后才能展示。

现有问题池模型优先复用；如需新增，可考虑 `paul_conversations`, `paul_messages`, `question_drafts`，通过 `user_id`/匿名会话令牌授权。不要让 API 直接依赖模型厂商的公开前端 SDK；密钥只留服务端。

### 匿名与隐私

- 登录非必要时，可允许短期匿名会话；匿名会话需不可猜测的 token，设到期和速率限制。
- 聊天内容默认仅当前用户可见；不应直接进入公开问题池，不应默认用于市场营销或模型训练。
- 提交时显示“将发布哪些字段”；用户可编辑和删除任何敏感信息。
- 对输入长度、文件上传（如未来支持）、HTML 输出做校验和转义；不要在 Prompt 或日志中泄漏 Cookie、密钥、个人数据。
- 限制每会话上下文、请求频率及 token 开销；模型异常时提供原有手动提问表单作为退路。

## 6. 与课程和公共问题池联动

- 分类 `solve / create / explore` 与 COURSE_CONSTITUTION 一致。
- 若有对应的 **真实已发布课程**，Paul 可建议“直接开始课程”或“继续完善任务卡”，而不能强迫跳转。
- 若没有课程，Paul 仍应提供初步拆解，并允许提交问题池。
- 公开问题列表保留独立入口，不直接显示或检索私人聊天记录。
- 管理端只处理用户确认提交的任务卡；审核后才能公开。
- 长期可以将高质量问题转化为直播选题或 100 分 Series，但 MVP 不自动创建课程。

## 7. UI 和主题实现

遵循 THEME_SYSTEM 和当前 Pop 主题：语义组件如 `AppChatPanel`, `AppChatBubble`, `PaulAvatar`, `AppTaskDraft`；不要命名为 `PopChatPanel`，不要写死黄色/黑色。优先使用 `--color-*`, `--shadow-*`, `--radius-*` tokens。

- 聊天消息可读性优先，装饰集中在标题、Paul 头像、任务草稿标签。
- 表情只在状态变更时播放一次，`idle` 足够安静。
- 提供 Enter 发送、Shift+Enter 换行、可见 focus、高对比度、`aria-live` 和 `prefers-reduced-motion`。
- 推荐按钮是真实链接；草稿保存与提交必须有服务端成功反馈，不能用纯动画冒充成功。

## 8. Sprint 与验收

**P0 / S1 — 页面改造**

- 复用原 Paul SVG / 角色组件；问题池主页以聊天为主，公共问题列表保留入口。
- 四个表情动作可从 UI 测试状态触发。
- 本地无 AI 时可使用**明确标注演示模式**的规则回复演示交互，不能对用户谎称模型已连接。

**P0 / S2 — 真实 AI 与结构化草稿**

- 接入服务端 LLM、真实多轮上下文和结构化任务卡。
- 任务卡实时更新，用户可编辑；不捏造不存在的课程。
- 添加速率限制、错误恢复、后端输入/输出校验。

**P0 / S3 — 提交与问题池联动**

- 用户可在提交前预览公开字段，明确同意后提交。
- 服务端返回实际保存结果和 ID，状态 `pending_review`；审核逻辑沿用原系统。
- 不提交时聊天绝不出现在公开列表。

**P1 / S4 — 质量与扩展**

- 日志仅保留必要的运营指标；消息持久化/清理策略可配置。
- 移动端、键盘、reduced-motion、异常场景和课程推荐的端到端测试。

### 必测用例

1. 模糊输入只追问一件事；明确输入快速产出草稿。
2. Solve/Create/Explore 三类都能正确处理；Explore 允许“实验失败但完成”。
3. 未点击公开提交时，公共问题池无任何私人草稿内容。
4. 用户修改任务卡后，最终持久化的是**修改后的版本**。
5. 模型超时、断网、速率限制后可重试，聊天记录不重复提交。
6. 未登录用户无法读取其他会话；请求无法跨用户篡改草稿。
7. 推荐课程来自数据库，不产生虚假链接。
8. Paul 四种表情、桌面/手机视图和 reduced-motion 正常。
